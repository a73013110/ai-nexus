# 0021 其他系統的檔案以短期憑證提供

- **狀態**：採用（2026-10-26）
- **實作**：Platform 的 `IRemoteFileSource`（每個來源一個實作，例如公文系統的 `GdFileSource`）；Features 的 `Platform/RemoteFiles` 發憑證（`RemoteFileTickets`）並提供 `GET /api/v1/remote-files/content`。前端以 `ReaderTarget.remote` 交給既有的閱讀器與檔案清單。
- **決定**：
  - 其他系統的檔案網址只在後端組，瀏覽器只拿到憑證：加密並簽章（Data Protection）的來源、位置、檔名、使用者與到期時間。
  - 權限只在發憑證時判斷一次，由擁有那筆資料的模組決定（例如出勤：看得到出勤紀錄就看得到附件）；下載端點只驗憑證本身。
  - 憑證只給發給的那位使用者用，`RemoteFiles:TicketMinutes`（預設 30 分鐘）到期；放在查詢字串。
  - 內容整個讀進記憶體再回傳（有大小上限），回應沿用上傳檔案的沙箱標頭；預覽與下載共用一個端點。

## 為什麼不直接給原系統的網址

- 公文系統的 `fileservlet` 沒有權限檢查，知道路徑就能下載；路徑又可從單號推得。網址出現在瀏覽器（網路面板、歷史、轉貼）等於公開。
- 透過本系統取回時，看得到哪張單的附件跟著本系統的資料範圍走，也留在本系統的速率限制與日誌裡。

## 為什麼用憑證而不是「單號＋附件序號」的端點

- 下載端點不必知道每種資料的權限規則：出勤、日後的簽呈或其他系統各自在發憑證前判斷，不用每加一種來源就在下載端點加一段權限判斷。
- 憑證帶著已驗證的位置，下載時不必再查一次來源資料庫。
- 代價是憑證會過期：使用者開著對話框太久後預覽失敗，訊息請他重開表單取得新憑證。

## 為什麼放查詢字串、到期時間自己檢查

- 加密後約三、四百字，超過 IIS 單一路徑段 260 字的上限。
- `ITimeLimitedDataProtector` 用系統時鐘，測不了過期；到期時間寫在內容裡、以 `TimeProvider` 檢查。

## 何時重新評估

- 原系統提供有權限檢查的 API 或可簽署的短期網址時，可改為轉址，不再經本系統傳送內容。
- 需要預覽很大的檔案（影片、大型掃描檔）時，改為串流並支援 Range，而不是整個讀進記憶體。
