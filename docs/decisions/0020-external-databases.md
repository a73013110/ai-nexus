# 0020 外部資料庫的存取

- **狀態**：採用（2026-10-25）
- **實作**：Platform 的 `ExternalDatabase<T>`、`AddExternalDatabase<T>()`；公文系統 GD 是第一個（`Features/Platform/Gd/`）。寫法見 [外部資料庫](../architecture/external-databases.md)。
- **決定**：
  - 讀其他內部系統的資料直接連它的資料庫，以固定、參數化的 SQL 查詢；不經 API 中介，也不對應進 EF。
  - 所有存取經同一個入口：降級、失敗分類、監控與日誌寫一次，每個系統只寫定義。
  - 該系統的連線設定只在 `Databases:<Name>`（含命令逾時與唯讀），不另開設定區段。
  - 業務 SQL 寫在使用端模組；系統模組只放多個模組共用的知識（如帳號對應）。

## 為什麼直連資料庫

- 公文系統等舊系統沒有可用的 API；另寫一層服務只是把同樣的 SQL 搬到別處，多一個要部署、監控的元件。
- 直讀別人的資料庫會綁住對方的結構，這是它的代價。以集中入口（防腐層）、固定 SQL、最小權限帳號與「查詢被拒」監控（對方改版時立刻看得到）控制。

## 為什麼不對應進 EF

- 結構不歸本系統管，不能進 `database/App/` 的匯出與 dacpac（[ADR 0010](0010-database-first-schema.md)），也不能加進唯一的 `AppDbContext`（[ADR 0003](0003-single-dbcontext.md)）。
- EF 的模型檢查與 migration 思維都假設結構由自己控制；對方改欄位時應該降級，而不是啟動或查詢時拋例外。

## 為什麼要統一入口

- 對方停機不能拖垮本系統：每個呼叫端都要「連不上回 null、取消照常拋出」，分散實作必然有漏網的路徑。
- 停機期間每次開頁都會失敗，日誌要去重；監控要能在沒人使用時探測。這些與哪個系統無關。
- 先前 GD 的存取放在「資料來源」模組，與它的瀏覽頁混在一起，出勤、組織都得依賴一個不相干的模組；改成每個系統一個薄模組後依賴方向單純。

## 何時重新評估

- 對方系統提供穩定的 API 或事件時，改用它並移除直連。
- 需要定期把外部資料複製進來（而不是即時查詢）時，另設計同步與刪除規則，不擴充這個入口。
