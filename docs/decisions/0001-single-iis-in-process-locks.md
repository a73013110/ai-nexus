# 0001 單一 IIS 執行個體與程序內鎖

- **狀態**：採用（2026-10）
- **決定**：正式環境只跑一個 IIS 執行個體、一個 worker（不開 web garden、不重疊回收）。資料規則靠資料庫鎖保證，本機與 IIS 共用資料庫時一樣有效；程序內鎖只留給生成排程這類程序內狀態。
- **修訂**（2026-11-02）：全域的程序內寫入鎖不再使用，見下方「資料規則改用資料庫鎖」。

## 原因

- 使用者是單一學校，一台主機的容量足夠；多台需要的分散式鎖、共用佇列與共用 key ring 會讓維運成本倍增。
- 程序內鎖依鍵分開，不同對話或資源互不等待，沒有全域瓶頸。
- 需要跨程序正確性的地方都用 SQL 處理：配額與附件容量用 row lock，生成用 executor 租約，背景工作用 fenced lease，所以本機與 IIS 共用資料庫時不會互相中止生成。

## 資料規則改用資料庫鎖

程序內 semaphore 在兩個程序各有一把，實際上沒有互斥；全域的還會讓無關的寫入互等，或包住檔案讀取與 Argon2。`sp_getapplock` 要在交易內，所以取鎖點都重新放在交易的第一步，耗時工作移到鎖外。

| 原本的鎖 | 保護的規則 | 現在 |
| --- | --- | --- |
| `IdentityWriteLock` | SID 與帳號綁定、登入失敗次數 | 目錄登入建立或更新帳號時取行政寫入鎖（與帳號管理同一把）；沒有變更的登入不取鎖。本機帳號鎖該使用者的列，雜湊在鎖外計算 |
| `KnowledgeWriteLock` | 向量模型只有一個啟用中、重建與清除互斥；文件片段的差異寫入 | 模型生命週期取行政寫入鎖，模型沒換的查詢不取鎖；片段寫入鎖文件列 |
| `AttachmentWriteLock` | 配額、檔案引用 | 拿掉：擁有者的 `Users` 列鎖本來就涵蓋。跨擁有者的規則（知識庫文件上限、刪除知識庫）用依知識庫分鍵的 `DocumentWriteLock` |
| `PunchImportGate` | 同一檔不重複匯入、寫入順序等於開始順序 | 讀檔與解析不持鎖；提交前取匯入鎖（[ADR 0032](0032-administrative-write-begin-commit.md)），排程在鎖內再判斷一次是否還要匯入 |
| `ResourceWriteLock` | 版本化儲存、ACL 變更與刪除互斥；每人上限與評分唯一 | 依資源的應用程式鎖，鎖後才檢查資源是否還在。每人的規則改鎖 `Users` 列（`UserRowLock`），不再用字串範圍 |
| `ShareWriteLock` | 有效分享上限；建立與撤銷 | 拿掉：上限由 `Users` 列鎖涵蓋，撤銷是單筆可重複的更新。分享成果另取資源鎖，與刪除成果排隊 |
| `RepositoryWriteLock` | 釘選上限、連線唯一、留言只貼一次 | 拿掉：每人的規則改鎖 `Users` 列；它還包住讀 diff 與貼留言，一人等 Gitea 全站的寫入都要等。留言改為條件式 UPDATE 認領（記在 `CommentedAt`，附租約），不開交易等網路 |

Serializable 也一併拿掉，因為它在 RCSI 下只擋得住「檢查之後才插入」，擋不住已通過檢查的對方，範圍鎖還會讓不相關的工作互等：

- 刪除專案等容器時「不能有進行中的工作」改用 [`ContainerLock`](../../backend/src/AiNexus.Features/Work/Collaboration/ContainerLock.cs)：開始工作取共用鎖、刪除取獨佔鎖，同容器的工作彼此不等。
- 向量模型生命週期改用行政寫入鎖，唯一索引（`Key`、啟用中的 `Status`）是最後防線。

取鎖順序固定為應用程式鎖（資源 → 容器）→ `Users` 列（依 ID 排序）→ 其他列；背景工作是工作列 → 文件列。順序意外反過來時由 SQL Server 的死結偵測解開，不會寫出錯誤資料。

### 仍在程序內

| 鎖 | 為什麼留著 | 跨程序時的後果 |
| --- | --- | --- |
| `GenerationScheduler` 的對話鎖與模型容量 | 協調程序內的串流狀態與模型併發，資料規則另有 `Users` 列鎖與租約 | 容量各算各的 |

## 代價

- 聊天排程與模型容量（`MaxConcurrency`）只在程序內有效，沒有跨主機的 GPU 限制或全域持久佇列。
- 留言認領後程序中止時，租約內不能重送，到期重送可能重複留言；留言無法與資料庫一起回復，這是取捨。
- 把對話或成品歸到專案不取 `ContainerLock`：與刪除專案同時發生時，可能留下指向已軟刪除專案的欄位。這不涉及進行中的工作，所以不擋。
- 回收或重啟會中斷正在生成的回答（租約到期後保留部分輸出，可重新生成）。

## 何時重新評估

要同時跑多台伺服器時：其餘程序內鎖改為資料庫併發控制（應用程式鎖、rowversion 或條件更新），匯入改成資料庫層的預約與唯一約束，監控的 presence 改成分散式 adapter，Data Protection key ring 改為共用。見 [生成與背景任務](../architecture/generation.md)。
