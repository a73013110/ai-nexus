# 0017 組織單位與資料範圍

- **狀態**：採用（2026-10-18）
- **實作**：已完成。Organization 模組（部門樹、人員所屬、`OrganizationDirectory`）見 [組織](../features/organization.md)；資料範圍（授權加範圍、`IDataScope`、範圍宣告掛在 [ADR 0016](0016-areas-urls-and-navigation.md) 的頁面目錄上）見 [資料範圍](../architecture/data-scopes.md)，第一個套用的功能是活動稽核。
- **決定**：
  - 角色決定「能做什麼」，組織單位與範圍決定「能看哪些資料」；不用角色切資料。
  - 新增 `Organization` 模組（區 `admin`），管理部門樹與人員所屬。
  - 授權從（群組, 功能）變成（群組, 功能, 範圍）。

## 角色與部門分工

- **角色＝職能**（工程師、技服、管理員），透過群組取得功能。
- **部門＝在組織中的位置**，只用來計算資料範圍與主管關係。
- 不用角色切資料：「A 部工程師」「B 部工程師」做成角色，數量會隨部門 × 職能相乘，調部門還得改授權。

## 範圍

| 範圍 | 意思 | 例 |
|---|---|---|
| `own` | 自己建立或擁有的資料 | 對話（現在的 owner 檢查） |
| `assigned` | 業務上被指派的關係 | 專案成員、負責的客戶 |
| `unit` | 自己所屬單位成員的資料 | 部門出勤 |
| `unit-tree` | 所屬單位及所有下層單位 | 處長看全處 |
| `all` | 全部 | 人資、稽核 |

- 範圍存在群組功能授權上，一筆授權一個範圍；使用者屬於多個群組時，各範圍條件以 OR 合併。
- 每個功能在頁面目錄宣告支援哪些範圍，管理介面只能選這些；沒有資料列概念的功能（例如系統設定）不設範圍。
- 平台提供 `IDataScope`：輸入功能，回傳使用者的有效範圍與相關單位 ID。同一個 request 內與功能授權共用同一次讀取。
- 模組自己把範圍轉成查詢條件（EF 的 Where 或預存程序參數）。沒有範圍就沒有資料；查不到的單筆一律 404，不透露資料存在。
- `assigned` 的關係由業務模組擁有並自行判斷，平台只回答「此使用者對此功能有 `assigned` 範圍」。
- 敏感欄位（例如身分證字號）用動作權限控制（`<module>.<page>.sensitive`），不混進範圍。

不採用：

- **EF 全域查詢篩選**：它不知道目前是哪個功能在查，也能被 `IgnoreQueryFilters` 繞過；明確寫在查詢裡並配測試比較可靠。
- **SQL Server Row-Level Security**：留作日後的深度防禦，不當主要機制。

## 主管範圍

- **決定**：範圍原則上存在群組授權上；例外是功能在頁面目錄宣告「主管範圍」（`unit` 或 `unit-tree`），組織管理勾選為主管的人對其任主管的單位自動取得它，與群組範圍 OR 合併。第一個宣告的是出勤紀錄（`unit-tree`），規則見 [資料範圍](../architecture/data-scopes.md#主管範圍)。
- **理由**：主管是誰已經記在組織的主管勾選上；再建「主管群組」等於兩份主管資料，調任或卸任時只改一邊，範圍就會錯。來源只有一個，組織改了範圍就跟著改。
- 主管範圍不授予功能：仍要有功能授權，沒有就是 403；它只決定看得到誰。
- **取捨**：管理員無法在群組上關掉某功能的主管範圍；要取消只能改主管勾選（同時影響所有宣告的功能），或從目錄拿掉宣告（全部主管一起失效）。所以只在「主管看部屬」是業務預設的功能宣告，稽核等不宣告。
- 不採用：每個主管單位一筆自動產生的群組授權——仍是兩份資料，還要同步。

## Organization 模組

- 資料表 `organization.Units`（樹狀、啟用、排序）與 `organization.UnitMembers`（使用者、單位、是否主要所屬、是否主管）。
- 管理頁 `/admin/organization`，選單上放在「身分與權限」分群底下（選單是資料，模組各自獨立）。
- 不放進 AccessControl：部門是組織資料，不是授權資料；出勤、請假等員工服務讀部門與主管時，只需要 Organization 的 public 服務。
- 依賴方向是 Organization → AccessControl（沿用授權目錄、policy 與 `AdministrativeAudit`），業務模組 → Organization。AccessControl 被所有模組引用，反過來依賴 Organization 會成環：資料範圍需要所屬單位時，由 AccessControl 定義介面、Organization 實作，同 `IRequestActor` 的做法（原本寫成 AccessControl → Organization，實作時修正）。
- 只記錄目前所屬。「當時在哪個部門」（例如去年的出勤歸屬）由業務資料在寫入時自己存單位 ID，不靠組織歷史表。
- 部門與所屬由管理員維護，不從 AD 同步：AD 的部門屬性不可靠，同步只會把錯誤帶進資料範圍。
- 補註（2026-10-23）：部門樹與主管改為可從公文系統 GD 匯入（[組織](../features/organization.md#從公文系統匯入)）。GD 的部門與主管是公文簽核實際在用、有人維護的資料，與 AD 屬性不同；匯入先預覽再套用，匯入的單位以 GD 為準，手建單位與一般成員仍由管理員維護。讀 GD 的 `GdUnitSource` 放在 Organization，經 Gd 模組存取（[ADR 0020](0020-external-databases.md)）。

需要代理、委派（某段期間代理他人）或跨單位的臨時範圍時，再評估擴充範圍類別。
