# 0031 行政寫入依範圍以資料庫鎖排隊，不用 Serializable

- **狀態**：採用（2026-11-02）
- **決定**：`AdministrativeWrite` 在 READ COMMITTED（RCSI）交易內先取 `sp_getapplock`，鎖隨交易釋放。範圍由 `AuditTarget.Feature` 推得：一個模組一把，帳號與存取控制共用一把。不再用程序內的全域 semaphore，也不再用 Serializable。
- **修訂**：[ADR 0001](0001-single-iis-in-process-locks.md)（行政寫入不再是程序內鎖）。

## 原因

- **全域鎖不隨功能成長**：卡片、郵件、組織彼此無關卻互相排隊，一筆慢的組織匯入會擋住所有模組的管理操作。
- **程序內鎖不跨程序**：本機與 IIS 共用資料庫時各有一把，實際上沒有互斥，只剩 Serializable 保護。
- **單純拿掉全域鎖不可行**：每筆寫入都在交易內讀權限表，Serializable 的範圍鎖會讓不同模組與角色變更互等，甚至死結。
- **範圍是模組而不是資源**：模組內的規則常跨多列（整棵單位樹、整份選單、同一張卡的所有期間），沒有單一資料列可鎖；開發者也不必為每個寫入判斷鎖什麼。
- **帳號與存取控制共用**：兩者都會改變誰持有什麼功能。分開鎖時，兩位管理員可以互相撤權，並都在對方提交前通過 lockout 檢查。

## 代價

- **鎖外的寫入不再被擋**：本機登入、本人改資料這類不取鎖的寫入可能撞上同一列，由唯一索引與並行控制欄位擋下，回可重送的 `admin_write_conflict`。規則要靠鎖才成立、又有鎖外寫入者時，對方也要取同一把鎖（刷卡匯入、目錄帳號登入、向量模型的自動建立與啟用都是如此）。
- **同模組仍然排隊**：等候有上限（`AccessControl:WriteLockTimeoutSeconds`），逾時回 `admin_write_busy`，所以耗時工作不放進 mutation。

## 何時重新評估

某個模組的管理寫入常等到逾時：先把耗時工作移出 mutation；仍不夠才讓該模組依資源分鍵，並確認沒有跨資源的規則。
