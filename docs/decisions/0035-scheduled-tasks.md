# 0035 排程任務：一個引擎、資料庫租約、任務只寫業務邏輯

- **狀態**：採用（2026-11-08）
- **決定**：
  - 定期工作一律實作 `IScheduledTask`，由 `Admin/Scheduling` 的單一引擎執行；原本各自的 `BackgroundService`（通知過期、事件保存期、郵件保存期、分享與附件清理、結構異動檢查、部署紀錄、打卡匯入、日曆同步、向量佇列與保存期）全部改寫成任務。
  - 跨程序互斥用 `scheduling.ScheduledTasks` 的租約：條件式 `UPDATE` 認領、定期續租、`LeaseToken` fencing 寫回，與背景工作佇列同一套作法（[ADR 0001](0001-single-iis-in-process-locks.md)）。日曆同步原本的 `sp_getapplock` 與記憶體狀態一併移除。
  - 每輪寫一筆 `ScheduledTaskRuns`（狀態、進度、摘要、錯誤代碼與查證代碼），管理頁、監控來源與失敗通知都讀這份資料；沒事可做的紀錄只留 2 天。
  - 排程的程式宣告是預設值，設定 `Scheduling:Tasks:<Key>` 可覆寫；`Scheduling:Execute` 決定哪個程序執行。
  - 使用者送出的佇列（背景工作、郵件、生成）不併入：它們是逐筆認領的佇列，不是定期執行；管理頁以另一個檢視列出背景工作佇列。
- **原因**：
  - 背景工作越來越多，卻看不到有哪些、下次何時跑、是否在跑、結果如何，也不能手動執行或停止；每個 worker 各自寫迴圈、例外處理、日誌與間隔設定，重複且行為不一（有的啟動即跑、有的吞例外、有的沒有日誌）。
  - 開發機與正式站共用資料庫：程序內的計時器無法互斥，兩邊會同時清理或同步。租約讓任一時刻只有一個程序在跑，`Execute` 讓開發機完全不參與。
  - 狀態放資料庫，任何程序回應的管理頁看到的都一樣，重啟後也知道上一輪的結果。
- **取捨**：
  - 每個任務一列、每輪一筆紀錄，多了兩張表與寫入；間隔最短的任務是每分鐘，紀錄量以保存期控制。
  - 到期後最多晚 `PollSeconds`（預設 5 秒）才開始；同一程序內的手動要求會立即喚醒。
  - 任務必須可重複執行（停站、停止、逾時都可能中途打斷），寫法比單純的迴圈嚴格。
- **延伸**：[排程任務](../architecture/scheduled-tasks.md)、[背景作業](../features/scheduling.md)。
