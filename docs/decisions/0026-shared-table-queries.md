# 0026 表格的排序、篩選與分頁由共用元件處理

- **狀態**：採用（2026-10-28）。新頁面與改到的列表照此做；尚未遷移的頁面改到時再換。
- **實作**：前端 [`table-model.ts`](../../frontend/src/app/shared/ui/table-model.ts)（`localTable`、`endpointTable`、`cursorTable`）與 `th[nxHeader]`；後端 `AiNexus.Platform/Data/Tables` 的 `TableRequest`、`TableColumns<T>`、`TablePage<T>` 與 `ToTablePageAsync`。
- **決定**：
  - 頁面只宣告欄位（ID、標題、可否排序、篩選型別、可否隱藏）與資料來源；排序、欄位篩選、分頁、載入狀態與分頁列都由表格模型處理，頁面不再自己接 `busy`、`count`、`pageChange`。
  - 儲存格照常寫 `<td>`：欄位定義只管行為，外觀（徽章、rowspan、卡片模式）仍由頁面的模板決定。
  - 查詢的形狀前後端只有一種：排序（預設單欄）、欄位篩選、`offset` 或 `cursor` 分頁。後端以欄位對應表（欄位 ID → 運算式）套用，沒宣告的欄位一律拒絕，排序一定補上主鍵作為同值的次序，`limit` 有上限。
  - 資料來源分三種，頁面不選「伺服器端或用戶端模式」：
    - `localTable`：資料本來就在前端，全部在前端處理。
    - `endpointTable`：符合 QueryBar 條件的總數不超過門檻（預設 500）時，後端一次回傳全部並標 `complete`，之後的排序、欄位篩選與換頁都在前端完成，不再呼叫 API；超過門檻才逐頁向後端讀取。
    - `cursorTable`：大表（日誌、稽核、寄送紀錄），只能依有索引的欄位排序，不計總數。
  - 篩選分兩層，但已套用的條件只顯示成同一列 chip：QueryBar 決定撈哪一批資料（區間、單位、人員，寫入 URL，改了一定重新查詢）；欄位篩選只在這一批裡縮小範圍，和排序、分頁一樣不寫入 URL。
  - 欄位篩選型別固定為文字、選項（多選，是否也用它）、數字範圍、日期範圍（時間點或日曆日）；選項在前端處理時可由資料算出，逐頁讀取時只提供欄位宣告的固定選項。需要後端算選項（facets）時再擴充。
  - 渲染有預算：以列分頁時一頁最多畫每頁筆數上限（100）列。以群組分頁、每個群組整段展開的頁面（出勤紀錄每人列出區間內每一天）一頁可達數千列，每個群組捲到附近才建立（`nearViewport`）。虛擬捲動不當預設。
  - 匯出直接使用同一份查詢，匯出內容與畫面上的排序、篩選一致。

## 為什麼不讓各頁自己做

- 到 2026-10 已有 24 個頁面用 `DataTable`：有的在後端各寫一套 `Skip`／`Take`／`Count`，有的在前端自己 sort、filter、slice，只有系統日誌用到排序表頭，沒有任何頁面有欄位篩選。同樣的事寫了很多遍，行為也不一致（同值的次序、讀取中能不能再按、換頁是否回到頂端）。
- 共用之後，新頁面要排序或篩選只是在欄位定義加一個選項；後端同樣只是在對應表多加一欄。

## 為什麼不像 Kendo 那樣先選伺服器端或用戶端模式

- 一開始就得猜資料量，猜錯要改寫；資料量又會隨時間成長，同一個功能可能今天幾十筆、明年上萬筆。
- 由後端依實際總數決定是否一次回傳全部，頁面寫法不變：資料少時排序與篩選即時、不打 API；資料多時自動改為逐頁查詢。
- 代價是同一套排序與比對規則要在前後端各實作一次，結果必須一致（中文排序規則、大小寫、時區）。前端 `applyLocal` 與後端 `TableQuery` 的測試涵蓋同樣的情境（同值次序、空值、大小寫、日期迄日）；某個欄位做不到一致時，那一欄只在後端處理。

## 為什麼欄位定義只管行為、不產生儲存格

- 以設定產生整張表（每欄寫格式、範本、樣式）的元件，碰到徽章、跨列的儲存格或手機卡片就得組合越來越多設定，最後比直接寫 HTML 還難讀。
- 表頭、排序、篩選、欄位顯示的寫法固定，適合宣告；儲存格內容每頁都不同，留給模板。

## 為什麼篩選分兩層

- QueryBar 的條件常常決定要讀哪些資料（區間越長資料越多），而且要能用連結分享；欄位篩選是看資料時臨時縮小範圍，換一批資料就沒有意義。
- 兩者合成一份 chip，使用者只看到一組「已套用條件」，不必分辨在哪裡設的。

## 為什麼渲染要有預算、虛擬捲動不當預設

- 資料讀完之後的渲染佔住主執行緒，載入動畫也跟著停下；分頁單位若是「群組」（例如每位人員帶出整個區間的每一天），一頁可以有數千列。
- 以列分頁不改變表格語意，是預設。群組要整段展開時保留以群組分頁，群組捲到附近才建立、之前放估計高度的佔位：第一屏立刻出現，DOM 只留看過的群組。逐格分批畫全部的列試過，不可行：每加一批瀏覽器就重排整張表（三千多列時每次約 90ms），總共要數十秒。
- 虛擬捲動和跨列儲存格、手機卡片、瀏覽器內搜尋與列印都有衝突，只在列高固定、列數上千時另外開啟。

## 何時重新評估

- 門檻內一次回傳全部仍太慢（每列很寬，或要附帶大量關聯資料）時，調低該端點的門檻，或改為只逐頁讀取。
- 需要多欄排序、使用者自己儲存的檢視（欄位、排序、篩選的組合）或分組小計時，在欄位定義與查詢擴充，不在頁面另做。
