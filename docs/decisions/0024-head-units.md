# 0024 首長單位帶領上層

- **狀態**：採用（2026-10-28）。
- **實作**：已完成。`organization.Units.HeadRank`、[`HeadUnits`](../../backend/src/AiNexus.Features/Admin/Organization/HeadUnits.cs)；規則見 [組織](../features/organization.md#首長單位) 與 [資料範圍](../architecture/data-scopes.md#主管範圍)。
- **決定**：
  - 單位可標為上層的**首長單位**，並有層級（1～9，數字越小越高）。首長單位的主管管轄上層，以及上層底下層級不比它高的子單位（含自己）與其下層。例如公司底下董事會設 1、總經理室設 2：董事長管全公司，總經理管總經理室與各處、不管董事會與其下的稽核部。
  - 上層有首長單位時，主管由首長單位擔任：上層自己不能勾選主管，設定當下取消既有的勾選，GD 匯入也不再同步它的主管。
  - 只改主管範圍。成員範圍（`unit`、`unit-tree`）仍照單位樹，總經理室的成員不會因此看到全公司。
  - 本地設定，GD 匯入不覆寫；單位被匯入搬到別的上層時清除層級。

## 為什麼

- 公文系統的部門樹照收發文排，常見公司底下董事會、總經理與各處同層。只靠樹，總經理只是「總經理室」的主管，看不到各處；GD 的公司主管又常是 `admin` 這類無意義的帳號。
- 主管跟著職位走：總經理換人時 GD 更新總經理室的主管，管轄自動跟著換，不必另外維護。
- 新增的處只要在公司底下，就自動歸首長單位管轄。

## 規則與取捨

- **層級而非單一代表**：同層可能有不只一個首長單位（董事會高於總經理），只允許一個表達不了。
- **不連鎖**：首長單位底下不能再有首長單位，管轄只看首長單位自己勾選的主管。連鎖時較低層級的首長會經由上一層擴大範圍，規則就難以預期。
- **失敗即拒絕**：首長單位停用或沒有主管時不管轄任何單位，也不改回上層的成員勾選；只有較高層級的失效時，較低層級照常。
- **首長單位的所有主管都管轄**，包含 GD 的副主管。如果副主管不該有同樣範圍，再在 `UnitMembers` 區分正副。
- 與各處同層、卻直接向董事會報告的單位，會落在總經理的管轄內（多看到）。真的遇到時再加「個別單位直屬某個首長單位」的設定。

## 不採用

- **本地改上層**（把各處掛到總經理室底下）：總經理室成員的「所屬單位及下層」會變成全公司；GD 匯入也會把上層改回去。
- **手動勾選總經理為公司主管**：匯入以 GD 為準會被覆蓋；換人時要記得改，跟人不跟職位。
- **群組給「全部」**：與組織無關，總經理會連董事會、稽核部都看得到，也不能表達主管關係。
- **第二棵「報告線」樹**：每個單位都要維護，新的處沒人設定時總經理就默默看不到；兩棵樹也難解釋。
